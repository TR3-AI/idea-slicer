Scrambled thoughts → parallel departments. The rules, the verified facts, and the FAQs.

The rules — how an idea gets sliced

Understand first. The whole idea is read end to end before anything is sliced. No slicing sentence-by-sentence.
Operating flow first. Every map starts with how the finished system runs, trigger to outcome — structure follows the flow, never the other way.
Departments, not tasks. A department owns a responsibility and runs in parallel. Shared state merges departments; a hard contract boundary splits them.
Genuine modules only. A module is a real building block (external adapter, stateful engine, non-trivial algorithm). One calculation or one config value is a feature, not a module.
Mobile is the primary screen. Bobby reads these pages on his phone. No visual change is done until verified at phone width (~390px) as well as desktop.
Terse chat, rich page. Chat replies carry only what changed; the page carries the full structure. ELI5 clarity, zero dumbing-down — technical terms stay, glossed in plain words.
Owner dependencies are explicit. Anything only Bobby can supply (keys, accounts, decisions) is listed as a blocking dependency, referenced by secret name — never stored raw.
Facts are decision-grade and near-verbatim. A fact earns its place only if a cold reader or agent would get the idea wrong without it — no restatements of the obvious. Each fact stays close to the source ruling's exact words and cites it; interpretation and plain-language explanation live in the FAQs, never in a fact.
Contradictions stop the line. Every new thought is checked against the pinned facts and rules before it is sliced — thresholds, better/worse directions, gate order. A thought that conflicts is never silently merged: both sides get quoted, the conflict is parked in Unresolved, Bobby rules, and the ruling cites both sources.

Facts — verified truths, trust these over guesses

1. An idea is a GitHub issue labeled idea; each added thought is a thought-labeled issue, auto-nested as a sub-issue of the idea by the robot.
2. The robot commits straight to main. Before every commit: stash, pull --rebase, pop — never push over the robot's head.
3. The robot auto-parks every new thought issue into the map's Unsorted lane. When that thought gets sliced, its park line is deleted.
4. A 422 "duplicate" when nesting a sub-issue means the robot already nested it — not an error.
5. The live page updates ~60–75s after the render run goes green. A curl grep on the live URL is the proof — a green run alone is not.
6. There are no unit tests. Verification = render run success + live-page grep for the feature string + a phone-width screenshot for any visual change.
7. The map file maps/<slug>.md is the source of truth; the issue body is a mirror, re-synced after every publish.
8. Chat history is expendable by design. Any agent resumes cold with: /ideaslicer — resume the <idea> idea (TR3-AI/idea-slicer issue #<n>).

FAQs

How do I add to an idea?Just talk. Each message becomes a thought issue and gets sliced into the map — no special format needed.
How do I continue in a new chat or with a different model?Use the resume line in Facts #8. Everything needed lives in the repo and the issues.
The robot and I edited at the same time — rebase conflict on a park line.Keep the sliced version (your side), drop the robot's park line, continue the rebase.
A thought I already sliced is still sitting in Unsorted on the live page.That's the robot's stale park line — delete it from the map and republish.
Leftover git stash entry from the publish rhythm?Inspect it with git stash show -p. If its content is already committed and live, drop it.
Do issue comments re-render the page?No — only issue body edits and new issues do.
